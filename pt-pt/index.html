Porquê

O software P2P ganha confiança sobrevivendo a sessões reais

O eMuleBB é ao mesmo tempo um esforço de produto e uma prática de engenharia: preservar um cliente Windows nativo complexo com comportamento de rede real e depois rodeá-lo de builds, testes, documentação, automação e provas de release modernos.

Motivo de produto

O eMuleBB é um produto próprio

O objetivo não é um mod cosmético, um fork de protocolo nem uma casca de transferências genérica. É uma linha eMule focada em banda larga para sessões longas, ficheiros raros, seeding deliberado e utilizadores avançados que ainda querem o fluxo de ambiente de trabalho nativo.

Motivo técnico

Tornar o comportamento P2P inspecionável

Slots de upload, timeouts, buffers, grandes bibliotecas, exposição do WebServer, controlo REST e evidência de pacote são tornados explícitos para que cada alteração possa ser revista, testada, documentada e ajustada.

Motivo de ecossistema

Construir as ferramentas em torno do cliente

A mesma disciplina de workspace abrange a aplicação, o tooling de controladores, os builds Windows, os serviços eD2K determinísticos e o trabalho experimental headless de eD2K/Kad sem fingir que cada projeto de laboratório é um produto estável para o utilizador final.

Funcionalidades

O que o eMuleBB acrescenta em torno do cliente clássico

O trabalho do RC2 foca o comportamento visível ao operador: política de upload previsível, binding mais seguro, limites fixos de desempenho, operação de grandes bibliotecas, automação local e evidência de pacote.

Partilha e upload

Controlo de upload em banda larga

Metas de slots limitadas, reciclagem de slots fracos, leituras de ratio e controlos de seeding mantêm úteis as ligações de upload rápidas sem alterar o protocolo de upload eD2K.

Controlo de rede

Binding, NAT e política de exposição

Binding consciente da interface, validação de mapeamento UPnP/NAT, HTTPS, regras de IP permitido e definições de bind do WebServer separadas mantêm as superfícies remotas explícitas e testáveis. Binding não é um kill switch de VPN.

Desempenho e escala

Predefinições atuais para sessões grandes

Buffers de socket maiores, limites de queue/source, file buffering, predefinições de timeout, sincronização recursiva de partilhas, trabalho de cache no arranque e orientação de long paths visam os sistemas Windows atuais e grandes bibliotecas.

Rede clássica

eD2K e Kad continuam em primeiro

A pesquisa Server, global e Kad continua a base nativa, com rastreio de identidade Kad, tratamento de nós maus, limpeza e trabalho de timing mantidos dentro dos limites de compatibilidade.

Automação

Fluxos REST e de controladores

Endpoints JSON autenticados cobrem transferências, pesquisas, ficheiros partilhados, servidores, Kad, logs, categorias, uploads, estatísticas, preferências e encerramento controlado a partir de ferramentas locais de confiança.

Segurança e proveniência

O RC2 é construído e empacotado no GitHub

RC2 publicado

emulebb-v0.7.3-rc.2 é uma prerelease do GitHub com ZIPs x64 e ARM64, pacotes de diagnóstico, manifestos, SBOMs e o bootstrapper da suíte.

Instalação verificada por hash

O bootstrapper transfere os assets do release e verifica os hashes dos pacotes a partir dos manifestos publicados antes de instalar.

Assets da suíte

O pacote aMuTorrent RC2 correspondente é publicado separadamente, e o fluxo completo de bootstrap x64 resolve-o automaticamente para a configuração do controlador.

SPDX SBOM

Release packages carry package-local SBOM.spdx.json plus sidecar *.sbom.spdx.json files, with manifest hashes that tie software contents to the exact package evidence.

GitHub provenance

RC2 assets are published from GitHub release automation with manifests, SHA-256 evidence, SBOMs, and a bootstrapper hash asset for verification.

Prova dos controladores

aMuTorrent, Prowlarr, Radarr, Sonarr, Torznab e as vias compatíveis com qBittorrent estão documentados como caminhos de integração local em torno do contrato nativo /api/v1.
