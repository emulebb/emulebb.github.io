eMuleBB 概要

Nightlies → Beta 2 → MFC 0.7.3

eMuleBB Rust 是活跃的 eD2K/Kad beta 客户端；nightly 是主要测试渠道，Beta 2 是正式基线，MFC 是维护中的 Windows 产品线。

这里是 eMuleBB 的所在地：eMule broadband edition，一个面向仍然看重 eMule 分布式共享模型、并希望像现代软件那样运行它的人的独立产品。0.7.3 软件包已在 GitHub Releases 发布，附带完整套件引导程序、独立 ZIP、清单、哈希、SBOM 以及配套的 aMuTorrent 控制器资源。

为什么

P2P 软件靠在真实会话中存活来赢得信任

eMuleBB 既是一项产品努力，也是一种工程实践：保留一个具有真实网络行为的复杂原生 Windows 客户端，然后用现代化的构建、测试、文档、自动化和发布证据将其包围。

产品理由

eMuleBB 是一个独立产品

目标不是表面修改的 mod、协议分叉或通用下载器外壳。它是一条面向宽带的 eMule 产品线，服务于长时会话、稀有文件、有意做种以及仍然想要原生桌面工作流的高级用户。

工程理由

让 P2P 行为可检视

上传槽、超时、缓冲区、大型库、WebServer 暴露、REST 控制和软件包证据都被显式化，使每项更改都能被审查、测试、记录和调整。

生态系统理由

围绕客户端构建工具

同一套 workspace 规范涵盖 Rust 客户端、控制器工具、原生构建、确定性 eD2K 服务、真实网络测试以及维护中的 Windows 客户端。

功能

eMuleBB 在经典客户端周围增加了什么

0.7.3 的工作聚焦于运营者可见的行为：可预测的上传策略、更安全的 binding、固定的性能上限、大型库运行、本地自动化和软件包证据。

共享与上传

宽带上传控制

有界的槽位目标、弱槽回收、分享率读数和做种控制，在不改变 eD2K 上传协议的前提下让高速上传链路保持有用。

网络控制

Binding、NAT 与暴露策略

感知接口的 binding、UPnP/NAT 映射校验、HTTPS、允许 IP 规则以及独立的 WebServer 绑定设置，使远程入口保持显式且可测试。Binding 不是 VPN 终止开关。

性能与规模

面向大型会话的现代默认值

更大的套接字缓冲区、队列/来源限制、文件缓冲、超时默认值、递归共享同步、启动缓存处理和长路径指引，针对当前的 Windows 系统和大型库。

经典网络

eD2K 和 Kad 仍居首位

服务器、全局和 Kad 搜索仍是原生基础，Kad 身份跟踪、坏节点处理、清理和计时工作都保持在兼容边界之内。

自动化

REST 与控制器工作流

经过认证的 JSON 端点涵盖传输、搜索、共享文件、服务器、Kad、日志、分类、上传、统计、首选项以及来自受信任本地工具的受控关闭。

测试与发布纪律

先有证据，后有标签

0.7.3 发布时附带 GitHub Actions 打包、清单、SHA-256 证据、SPDX SBOM、诊断资源以及引导程序哈希证据。

文档

指南、API 与发布说明

01

从产品指南开始

先把 eMuleBB 当作 eMule 使用：受信任的服务器、有意的 Kad bootstrap、可预测的 incoming/temp 路径以及可见的共享文件夹。

02

使用本地自动化

仅为受信任的控制器启用 REST，然后通过已记录的适配器路径使用 aMuTorrent、Prowlarr、Radarr 和 Sonarr。

03

阅读证据

安装、API、发布、SBOM 和软件包细节都在渲染后的文档中，使公开声明始终与受版本控制的证据绑定。

宽带发布线通过现有的 WebServer 监听器提供面向资源的 /api/v1 JSON API。它使用 X-API-Key 进行认证，返回 JSON 信封，并让原生 eMule 状态更改始终经由应用进行编排。

安全与来源

0.7.3 在 GitHub 上构建与打包

已发布的 0.7.3

emulebb-v0.7.3 是一个 GitHub 预发布版本，包含 x64 和 ARM64 ZIP、诊断软件包、清单、SBOM 以及套件引导程序。

经哈希校验的安装

引导程序在安装前下载发布资源，并依据已发布的清单校验软件包哈希。

套件资源

配套的 aMuTorrent 0.7.3 软件包单独发布，完整的 x64 引导流程会在控制器设置时自动解析它。

控制器证据

aMuTorrent、Prowlarr、Radarr、Sonarr、Torznab 以及兼容 qBittorrent 的通道，都被记录为围绕原生 /api/v1 契约的本地集成路径。
