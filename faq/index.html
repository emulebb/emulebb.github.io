FAQ

Using eMuleBB Rust

Start with the client, its packages and its operating model. The guides explain each workflow in full.

What is eMuleBB Rust?

A headless IPv4 eD2K/Kad client with a packaged browser console and authenticated REST API. It manages search, transfers and monitored shared folders.

Read more: First-launch guide

Which package should I download?

Choose the matching Windows, Linux or macOS package. Linux also has static-musl archives and container images. Android bundles are experimental developer artifacts, not an APK or a supported Android app.

Read more: Platforms and downloads

How do I open the browser console?

The implicit native first launch creates a private profile and prints the API key once. Open http://127.0.0.1:4711/ and enter that key. Keep all packaged WebUI files beside the client; existing profiles keep their existing key.

Read more: First-launch guide

How do networking and interface settings work?

Review server/Kad status, the chosen P2P interface and TCP/UDP reachability. REST control and P2P routing are separate; a loopback console does not imply offline networking or guarantee VPN safety.

Read more: Network setup

How do I share files?

Add deliberately chosen folder roots, review ignore patterns, and let recursive scanning and hashing finish. Sharing is managed as monitored folder trees. Add roots gradually rather than exposing an entire home directory.

Read more: Sharing workflow

Can I automate the client?

Yes. Authenticated /api/v1 requests use the X-API-Key header and the documented REST contract. The beta API can change; protect credentials and use the API consumer guide for requests and error handling.

Read more: REST API guide

What should I preserve before an update?

Stop cleanly and preserve the old binary, profile and payloads. An incompatible database schema requires a fresh profile; do not edit schema markers or delete the database to force reuse. Unfinished-transfer continuity across incompatible profiles is not promised.

Read more: Update and profile precautions

What does build validation establish?

Package smoke, checksums and provenance identify the tested source and scope. Native package checks are separate from historical public-network evidence, long-soak and large-library qualification. Review the platform guide for the published proof and its limits.

Read more: Platform evidence

How can I contribute or get help?

Use the repository that owns the affected code when reporting a reproducible problem. Contributors can start with the supported workspace, focused tests, API tools or documentation. Review private diagnostic bundles before sharing any evidence.

Read more: Contributor and support guide
